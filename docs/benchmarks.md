# Benchmarks

Generated by `make bench` (`bench/tests/cu.rs`); do not edit by hand. Compute units measured in LiteSVM 0.18 on the SBF build of `bench-program` (cargo-build-sbf 4.5.0, Default platform-tools: v1.57, Default Rust: 1.95.0, sBPF v3). Inputs: 1000 values or pairs from seed `0xf7f1c5be7c40002`: for `MulDown`, `DivDown` and `SqrtDown` magnitudes log-uniform in `[10^-6, 10^9]` with random signs (`sqrt` takes the absolute value); `exp` arguments uniform in `[−42, 43]`; `ln` arguments log-uniform in `[10^-6, 10^9]`; `norm_cdf` and `norm_pdf` arguments uniform in `[−9.25, 9.25]`; `MulShr` (`wide::mul_shr`, shift 64, rounding down) two `u128` with log-uniform magnitudes over the whole range; the Black-Scholes rows `S` log-uniform in `[10^-6, 10^9]`, `S/K` log-uniform in `[0.05, 20]`, `T` uniform in `(0, 30]`, `σ` log-uniform in `[0.005, 5]`, `r` and `q` uniform in `[−0.1, 0.5]`, calls and puts (the "near the money" rows take `S/K` within `±0.39%` instead: the other form of `d1`'s moneyness term); the implied-volatility rows the targets `price(σ)` of such inputs, drawn until 1000 are answered (`implied_vol` returns a value), and "all iterations" takes all `IV_MAX_ITERATIONS` steps (the bench-only `iv_bench::all_iterations`), its worst case. Every on-chain result equals the host result bit for bit, and two runs in fresh VMs give identical numbers. Release profile: `lto = "fat"`, `codegen-units = 1`; a program built with another profile will measure differently.

"Net" is the median minus the `Noop` median (175 CU), which covers the entrypoint, decoding one `FixedBytes` argument and return data. `MulDown` and `DivDown` decode two arguments, `MulShr` two plus a shift and a rounding, and the Black-Scholes rows a kind byte and six, so their net figures still include the extra decoding; the other rows decode one, like `Noop`.

## Representation comparison (milestone 3)

Measured at commit `6adf034`, where `make bench` reproduces it, with the inputs above: each candidate of `docs/PLAN.md` 4.1 on the same arguments and build profile. "Decimal, binary core" converts in and out of the 64-bit-digit kernel that Q64.64 uses; "decimal, native" runs the same reduction and polynomials as decimal `Fixed` multiplies. Net CU, `Noop` (164 CU) subtracted:

| Representation | `exp` median | `exp` max | `ln` median | `ln` max | `exp` + `ln` median |
| --- | ---: | ---: | ---: | ---: | ---: |
| Q64.64 | 337 | 352 | 460 | 465 | 797 |
| Q64.64, `ln` atanh form | | | 614 | 655 | |
| Decimal `10^18`, binary core | 462 | 479 | 470 | 529 | 932 |
| Decimal `10^18`, native | 7,989 | 8,122 | 9,051 | 9,186 | 17,040 |

Q64.64 is 15% cheaper than the best decimal form, outside the 10% band in which decimal would have won for its exact token conversions (`docs/PLAN.md`, decision log); it is also the more accurate (`docs/precision.md`).
